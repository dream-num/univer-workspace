# 大表 outline 阈值

操作者在 2026-11-13 看过下面的测量后决定：CLI daemon 的 `maxBoxCells` 用 **5,000,000**，
MCP 执行器用 **1,000,000**，执行器的 Lens 缓存预算用 512 MiB，CLI 缓存预算仍为 512 MiB。
Lens 和 Client Core 的缺省阈值仍为 500,000，宿主显式选择自己的阈值。超过阈值时，outline 返回一个
`block` 和 `sheet-lens-sheet-too-large` 警告，`read` 和 `find` 继续读取完整单元格视图。

这个取值高于下文「阈值规则」按半预算和 5 秒算出的 750,000。按本文测量，它带来以下后果：

- 估算条目字节超过 512 MiB 的表不进缓存，每次 `outline` 都重新导出和建模，并附 `sheet-lens-not-cached` 警告。
  按系数 12，约 1,500,000 格以上的十列流水表属于这种情况（每格约 359 字节；1,000,000 格估算 351,937,476 字节，未超过；2,000,000 格估算 717,581,832 字节，已超过）。
- 实测 2,000,000 格完整建模约 9.6 秒，常驻约 572 MiB。5,000,000 格未实测，按 1,000,000 到 2,000,000 格的
  趋势线性外推约为 25 秒和 1.4 GiB，仅供参考。live 验证中，接近 750,000 格的表在首次未命中时 daemon 加 worker
  的瞬时 RSS 达到约 1.6 至 2.3 GB，更大的表会更高。
- MCP 执行器的 1,000,000 格表常驻约 282 MiB、估算约 336 MiB，能进 512 MiB 缓存，但同时只能放下一张；
  建模约 4.5 秒，期间阻塞执行器主线程，见 issue #369。

阈值计算已用范围的外接矩形面积，不计算实际非空格数。只有 A1 和 Z20000 有值的表也占
520,000 格。面积等于阈值时仍检测区域。50,000 行数据加一行表头共 500,010 格，新的 CLI
阈值允许它生成表和十列摘要。旧测量中的 50,000 行包含表头，恰好 500,000 格，原来就没有
触发严格大于阈值的保护，不能把那次测量当成只生成 `block` 的基线。

## 测量方法

2026-11-13 在 Apple M2 Pro、10 核、32 GiB 内存、Darwin arm64 上运行，Node.js
24.19.0，Vitest 4.1.11。机器有其他任务，首次测量前的 load average 为
15.41、14.62、10.94，最终修正测量前最近一次观测为 18.64、19.82、16.97。没有停止其他任务。
最终测量期间没有同时运行本任务的测试或 profiler。这里不宣称相对旧版本的速度变化。

从仓库根目录运行以下命令。

```bash
SHEET_LENS_LARGE_MEASURE=1 SHEET_LENS_EXTRA_CELLS=750000 pnpm --filter @univerjs/univer-workspace-client-core exec vitest run test/sheet-lens/large-measure.test.ts --pool=forks --execArgv=--expose-gc
```

`large-measure.test.ts` 平时跳过。默认测量 100,000、300,000、500,000、1,000,000 和
2,000,000 格，`SHEET_LENS_EXTRA_CELLS` 加测候选阈值。每张表十列，第一行为粗体表头，
其余行有三列文本和七列数字，最后一列有已缓存值的公式。每个规模先预热一次，再测三次，
按正序、逆序、正序交替运行。每次创建独立 engine，`maxBoxCells` 等于该表面积，测量用的
缓存预算为 2 GiB，以便保留最大规模的条目。

每次内存读数前执行两次 GC，中间让出一个 event-loop turn，等待上一条目的 backing store 释放。
每个样本在基线 GC 后才由注入的 exporter 分配 UnitData。首次 outline 必须检测出覆盖整张表的
一个 table 和全部十列，且没有警告。随后强制 GC，读取 `heapUsed` 增量，包含 UnitData、
显示读取器、单元格视图和已建好的模型。另记 `arrayBuffers` 增量，补充不在 JavaScript 堆中的
检测器 typed arrays。最后通过缓存命中的 `find` 断言全部数据行均可搜索，且只导出过一次。
这些断言防止把降级、缓存命中或部分检测误报为完整建模。

表中的建模时间取 `prepareMs + operationMs`，包括 JSON 容量估算、显示文本、单元格视图、
feature grid、区域检测和列摘要，排除 exporter 和强制 GC。这比只计首次 outline 的
`operationMs` 更保守。堆增量、常驻合计和时间各取三次中位数。常驻合计为堆增量加
`arrayBuffers` 增量。估算条目字节为 UTF-8 UnitData JSON 字节乘以现有系数 12。

| 格数 | 完整建模中位数 ms（最小至最大） | outline 阶段中位数 ms | GC 后堆增量 MiB | 堆加 typed arrays MiB | 估算条目字节 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100,000 | 394.9（346.8 至 452.8） | 204.7 | 26.47 | 27.41 | 33,639,420 |
| 300,000 | 1245.8（967.2 至 1293.9） | 597.1 | 83.03 | 85.83 | 104,003,040 |
| 500,000 | 2184.0（1858.9 至 2271.6） | 993.9 | 132.28 | 136.95 | 174,841,440 |
| 750,000 | 2848.5（2583.4 至 2952.4） | 1552.5 | 204.42 | 211.43 | 263,389,440 |
| 1,000,000 | 4453.8（4070.4 至 4485.0） | 2150.9 | 272.75 | 282.09 | 351,937,476 |
| 2,000,000 | 9581.2（8710.3 至 9791.8） | 5323.3 | 553.43 | 572.13 | 717,581,832 |

750,000 格的三次常驻合计最大为 211.43 MiB，计费估算为 251.19 MiB，
完整建模范围为 2583.4 至 2952.4 ms。三次都低于 256 MiB 和 5 秒。
本地合成请求总耗时中位数为 3054.7 ms，包括 exporter，未计远程传输。

## 阈值规则（测量时的推荐，已被操作者的决定取代）

在实测候选中选择满足以下条件的最大值。

- 单表常驻堆不超过缓存预算的一半，CLI 为 256 MiB。
- 建模时间不超过 5 秒。

这里还检查常驻合计和缓存计费估算均不超过 256 MiB，并检查三次样本的最大值，而不只检查中位数。
750,000 格是补测的候选，不是从两端线性外推的结果。1,000,000 格的常驻内存已超过 256 MiB，
因此没有采用它。2,000,000 格也超过内存预算，建模时间还超过 5 秒。

`detect/features.ts` 的 `MAX_GRID_CELLS = 8_000_000` 未修改。本次最大面积为 2,000,000 格，
没有额外的格式或合并区扩大 grid，所有样本都断言完整检测，因而没有触发该保护。

## MCP executor 的建议（测量时的推荐，已被操作者的决定取代）

操作者选定执行器用 1,000,000 格和 512 MiB 缓存，由 MCP 工具的 PR 接入。下面是测量时按半预算规则给出的推荐。执行器获得 engine 后，按实际配置的 `EXECUTOR_SHEET_LENS_CACHE_BYTES`
选取实测候选，不能无条件复制 CLI 的值。

| 执行器 Lens 缓存预算 | 半预算 | 建议 `maxBoxCells` |
| ---: | ---: | ---: |
| 256 MiB | 128 MiB | 300,000 |
| 512 MiB | 256 MiB | 750,000 |

上述建议同时要求堆、typed arrays 合计和条目计费估算落在半预算内，且建模不超过 5 秒。
多用户执行器仍需按用户隔离缓存，并在容器的实际 CPU 配额、Node 版本和并发下重测。
预算更小或更大时，从本表实测规模中选符合条件的值，或补测新的候选。

## 适用范围

这些数字针对本次合成流水表。阈值不是任意 Workbook 的内存硬上限。长文本、样式、公式、
多个 Sheet、共享引用和额外对象都可能改变成本。超过阈值只跳过区域与列检测，仍需持有
UnitData 和单元格视图。缓存按整本 Workbook 的 JSON 字节估算，超预算条目仍按现有规则不入缓存。
本次没有改变缓存系数或准入策略。

强制 GC 后的堆增量不是进程 RSS，也不包含 worker、其他原生内存或临时导出和建模峰值。
2 GiB 的测量缓存不是 CLI 的新配置。测量没有访问远程 Workspace，`requestMs` 只包含本地
合成 exporter 和 engine，不能当作远程 CLI 的总延迟。

单独对生产构建的 750,000 格表运行 V8 CPU profile，确认十列完整输出。采样主要落在
`buildOutlineModel` 的 `profileColumn`、`profileCells` 及准备阶段的 `sheetCellsOf`、
`featureSheetOf`，限制来自单线程 CPU 工作和对象分配。该次采样的时间未用于阈值判断。

`workbookFromData` 的第五个参数和 `buildOutlineModel` 的第二个参数都接受 `maxBoxCells`。
直接调用 Lens 时，在准备和建模时传入相同值。提高模型阶段的值不能恢复准备阶段已经跳过的
feature grid。engine 负责把一个构造选项传给两个阶段，已有调用者继续使用缺省值。
